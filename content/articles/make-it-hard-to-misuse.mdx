<Define term="waystone-monads">Waystone.Monads</Define> is my port of Rust's `Option` into .NET. An `Option<T>` is either `Some` holding a value or `None` holding nothing, and the type makes you deal with the empty case before you can reach the value. <Define term="unwrap-method" code>Unwrap</Define> is the escape hatch, and it reaches in for the value and throws if there isn't one.

I watched an agent write this against it:

```csharp
if (option.IsSome)
{
    return option.Unwrap();
}

return 0;
```

It compiles, it passes tests, and it returns the right number. It is also the exact shape the library exists to remove. <ArticleLink slug="option-type-in-dotnet">The whole point is that absence stops being a surprise</ArticleLink>, and this asks whether there is a value and then reaches in anyway. Two questions where one would do, and the reader has to check for themselves that the answers agree. It should be a <Define term="match-method" code>Match</Define>, which takes one branch for `Some` and one for `None` so both cases get written down.

The agent kept doing it, and it is a good model. A C# developer's instinct is to check-then-access. That instinct is all over the training data. Nothing in my library stopped it. A human would have written the same thing, slower and one at a time.

## A rule in markdown is a rule you are hoping for

The reflex is to write it down. Add a line to `AGENTS.md` or `CLAUDE.md`, something like *prefer Match over a guarded unwrap*, and move on.

I have <ArticleLink slug="skills-that-teach">spent a long time on instructions that teach rather than dictate</ArticleLink>, so this is not a complaint about writing instructions badly. It is that a markdown instruction has properties you would not accept anywhere else in your toolchain. The model might follow it and might not. It competes for the <Define term="context-window">context window</Define> against everything else in the task, and it gets weighed again on every turn. It fails silently, so you find out by reading the diff. And the cost grows with the rule count, because ten guidelines is ten things the model has to hold in mind while also solving the problem you gave it.

Nobody would ship a type system with those properties. We accept them in agent instructions because writing prose is the cheapest thing available and it feels like doing something.

The alternative is to move the rule somewhere it executes. In .NET that means a <Define term="roslyn-analyzer">Roslyn analyzer</Define>, which runs inside the compiler on every build, and a <Define term="code-fix-provider">code fix provider</Define>, which rewrites the offending code in the editor. The rule stops being advice and becomes an outcome the model cannot talk its way past, and it costs nothing to check again because checking is what a compiler already does.

Something else falls out of that. One general instruction survives - the project compiles clean unless I approve a warning - and it does the work of all of them, because the rules now live in the build and nothing has to remember them. The win is compression rather than elimination. I did not delete the prose, I stopped adding to it.

## Documentation was always the cheap substitute

Scott Meyers wrote the rule I keep coming back to in <LinkNote href="https://www.aristeia.com/Papers/IEEE_Software_JulAug_2004_revised.htm" note="Scott Meyers, 'The Most Important Design Guideline?', IEEE Software, July/August 2004. Argues that interface design is where most avoidable defects are prevented or created.">IEEE Software in 2004</LinkNote>: make interfaces easy to use correctly and hard to use incorrectly. He wrote about C++, where the only enforcement available was the type system. Anything the types could not say became a naming convention and a hope that someone read the docs.

That constraint has not been real in .NET for years. Analyzers ship inside a <Define term="nuget">NuGet</Define> package, so installing a library can install its rules with no separate step. .NET's larger projects do this - StyleCop, xunit and Microsoft's own threading analyzers all ship rules alongside the code.

I did not, for four major versions. Writing an analyzer means walking syntax trees, resolving symbols through the semantic model, and building a test harness that asserts a diagnostic lands on the right span of text. That is days of unglamorous work for polish a determined reader of the docs did not need. I knew how to do it. I could not justify the time, and so the rules stayed in prose, where they were free.

## The tax on getting this right has collapsed

I built the suite over two days with Claude Code. The 5.5 release carries twenty-seven rules, seven code fix providers covering fourteen of them, and about 4,586 lines of analyzer and test code.

Two days of elapsed time is not two days of writing. 138 test methods ship with those rules, and 45 of them assert that a rule stays *quiet* on code that looks like a violation and isn't. That ratio is where the time went. The model produced syntax-tree traversal faster than I could have. The work left over was deciding which spans a rule must never touch, watching it fail that assertion, and narrowing it.

The polish I could not justify in a week I can now justify in an afternoon. I would not stretch that to any library at all - mine has a small and regular API surface, and one with a broader surface pays more than an afternoon by some amount I have not measured.

Deciding what to forbid did not get cheaper. The model wrote the traversal, and it did not decide which mistakes are bugs and which are habits. I won't claim my judgement was uncontaminated, because it proposed severities too and I cannot fully separate what I chose from what I accepted because it sounded right. The calls I remember making against it were about how loud to be.

## A guardrail only works at a severity its reader can see

That last part is where the real design sits, and it is the part a markdown file cannot express at all.

The rules ship in three tiers. Bugs warn, so they show up in build output. Idiom informs, so it surfaces in an editor and stays out of the build. Migrations ship disabled, because turning every nullable return into an `Option` is a project, not a defect. Nothing ships as an error.

That is the one call I did not think was mine to make. Some people using this library want idiomatic C# with a few monads in it. Others want to live inside the pipeline. A rule that fails the build decides that argument on the consumer's behalf, and the packaging makes it worse - the analyzer rides inside the library's own package, so a consumer bumping a patch version inherits every rule I have added since, with no opt-in and no route out but `.editorconfig`. A rule that fires on working code breaks a build nobody asked to change. That question - does this fire on code that worked yesterday - sat behind every one of them, and I do not think I got it right every time.

Here is the cost of that restraint, and it is the thing I would attack if someone else had written this. The guarded unwrap I opened with is an idiom rule. Idiom informs. So it never appears in build output, `TreatWarningsAsErrors` never sees it, and an agent working from a build log never learns about it. Reaching it takes one line from whoever installs the library:

```ini
dotnet_diagnostic.WM2004.severity = warning
```

My own repository does not set it. So the loop closes on the tier where a mistake is a bug, and the tier where a mistake is a habit still waits on somebody choosing to make it loud. A deterministic guardrail is only as strong as the volume you ship it at, and picking that volume is a judgement about your consumers that no amount of tooling makes for you.

What survives regardless is that the same artefact reaches a person. A developer sees a squiggle where the mistake is, and for fourteen of the rules a lightbulb that applies the fix, before any build and without reading anything. That is why the prose inside each rule is written for a human rather than compressed into a code. One of them explains itself like this:

> Checking IsSome and then unwrapping asks the same question twice and relies on the reader to see that the answers agree.

We cannot forget the human even while we fix what the agents do. The sentence that tells a developer why the pattern is wrong is also the sentence that gives a model enough to produce the right correction rather than the nearest one. A rule in `AGENTS.md` reaches exactly one of those two readers.

## Writing down what to forbid audits your own design

You cannot write a rule against a pattern without stating why it is wrong, and more than once the honest answer was that the library made it too easy.

`Result<TOk, TErr>` declares an <Define term="implicit-conversion">implicit conversion</Define> from each of its two type arguments, so you can hand back a bare value or a bare error and let the compiler wrap it. Give it the same type twice and the compiler cannot choose between them, so every implicit conversion in that file stops compiling. `Result<string, string>` is a type my library will happily let you declare and then refuse to let you use.

Nobody reported that. It came out of trying to write the rule, because you cannot describe the pattern to a compiler without first saying exactly what is wrong with it, and "the two conversions are ambiguous" is a sentence I had never been forced to write down. It happened more than once across the suite, and the result is that v6 changes the library itself rather than only the diagnostics that describe it.

I set out to correct an agent and ended up with a written specification of everything my own API gets wrong, which is a thing four major versions of shipping it had never forced me to produce.

## What a library owes its users now

I would not have written any of this a year ago. I would have written better documentation instead, and felt fine about it.

I no longer think that is a defensible trade. I changed my mind watching a model make the same mistake a hundred times faster than a person could, which made an old problem impossible to ignore at the moment the fix got cheap.

Analyzers are .NET's version of this and not every ecosystem hands you one, but the category is wider than the tool. A type that makes the bad state unrepresentable is a deterministic guardrail. So is a lint rule with an autofix, a schema that rejects the malformed payload, a test that fails on the regression, a CI gate that will not merge. What they share is that they execute, they cost nothing to run again, they fail loudly, and they reach a person and a model with the same artefact. What sits in a markdown file shares none of that.

The question worth asking about every guideline you have written down for an agent is whether it could be something that runs instead. Most of them can't. The ones that can are worth an afternoon, and you will find out something about your own design on the way.

The guarded unwrap that started this has an id now, a severity I picked on purpose, and a sentence explaining itself to whoever reads it next. Making it louder than a suggestion is a decision I left to the person installing the library, which is the part that was always the real work - deciding what your library forbids, and how loudly.
