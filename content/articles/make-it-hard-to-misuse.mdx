An agent wrote this against a library of mine, a .NET port of Rust's <Define term="waystone-monads">`Option` and `Result`</Define>. An `Option<T>` holds a value or holds nothing, and it won't let you read the value until you have said what happens when it's missing. A `Result` is either a success or an error, so a method that can fail says so in its return type instead of throwing.

```csharp
Option<User> user = _users.Find(id);

if (user.IsSome)
{
    var found = user.Unwrap();
    var saveResult = _users.Save(found.Activate());

    saveResult.InspectErr(error => _logger.LogError("Activation failed: {Error}", error));

    return Ok(found.Email);
}

return NotFound();
```

It compiles, it passes tests, and it returns the right thing on the happy path, so if you saw it in review you would probably approve it. There are two mistakes in it and they fail in completely different ways.

The first is the guard. <ArticleLink slug="option-type-in-dotnet">`Option` asks you to say what happens when the value is missing</ArticleLink>, and this code asks whether the value is there and then reaches in for it anyway with <Define term="unwrap-method" code>Unwrap</Define>, which throws when there's nothing to return. <Define term="match-method" code>Match</Define> would do the job, because it takes one branch for `Some` and one for `None` and you can't write it without handling both. The guard and the unwrap are two statements that have to agree with each other, and nothing keeps them agreeing through the next edit.

The second one is worse, and you probably read straight past it, because it looks like the error is being handled. <Define term="inspect-err-method" code>InspectErr</Define> runs the logging and then hands the same `Result` straight back, and it's that returned `Result` nobody uses. The save result gets captured and given a name and passed to a method, which is what makes the line read as diligence, and the failure still goes to a log and no further. The endpoint returns 200 whether the save worked or not. A reviewer scanning for a missing error path finds a logger call and moves on.

The agent kept writing both, and it's a good model. C# developers check before they access, they have done it for twenty years, and the training data is full of it. Logging an error and carrying on is just as well attested. So the agent wrote what a competent C# developer writes, and nothing in my library told it otherwise.

I moved both rules out of prose and into the compiler. Three things had to be settled to do that, and they come in this order: why a written instruction doesn't hold, how to tell which of your instructions could run instead of being read, and how hard each one should push once it does.

## Why I stopped adding rules to AGENTS.md

My first thought was to write it down. Add two lines to <Define term="agents-md" code>AGENTS.md</Define> - *prefer `Match` over a guarded unwrap*, *never leave a `Result` unused* - and move on. That's what everyone does, and it follows from how we've been taught to work with agents, which is that you curate what the model reads and the behaviour follows.

I've <ArticleLink slug="skills-that-teach">spent a long time on instructions that teach rather than dictate</ArticleLink>, and I still think that's the right way to write them. But writing one well doesn't make it run. The model reads it, weighs it against everything else in the <Define term="context-window">context window</Define>, and decides whether to follow it - again, on every turn. The turns it doesn't, nothing warns you, so you find out by reading the diff. And each rule you add makes the others weaker, because ten guidelines is ten things the model holds in mind while also solving the problem you actually gave it.

Nobody would ship a type system that worked like that. We put up with it in agent instructions because prose is cheap to write and it feels like doing something.

So put the rule where it runs instead. Written that way it isn't advice the model weighs any more, and re-checking it costs nothing, because checking is what the build is already doing.

My `AGENTS.md` now has one general instruction where it used to have a list, and it says to leave the build clean - so any warning in the output is either a real problem or something I suppressed deliberately. The rules themselves live in the compiler, so nothing has to remember them. I still keep prose in my repositories, but I've stopped adding to it.

## Which of your instructions could run instead

.NET gave me a <Define term="roslyn-analyzer">Roslyn analyzer</Define>, which the compiler loads and runs over your code on every build, and a <Define term="code-fix-provider">code fix provider</Define>, which offers the correction in your editor. Your language will offer something else. A type that makes the bad state unrepresentable does the same job, and so does a lint rule with an autofix, a schema that rejects a malformed payload, a test that fails on the regression, or a CI check that won't merge. All of them run on their own, cost nothing to run again, fail where you can see it, and say the same thing to a developer and a model. A markdown file does none of that.

Whether one of your rules can move comes down to a single question: can you say exactly what is wrong with the pattern, in terms of something in the code that a machine could be pointed at? If you can write that sentence, the rule can run. If you can't, it stays prose and gets re-weighed every turn.

Plenty of your lines can't, and that's fine. Mine tells an agent to change only what it must and leave adjacent code alone, and no build step will ever tell an edit I asked for from one I didn't, any more than it can compile taste.

Scott Meyers put it in one line in <LinkNote href="https://www.aristeia.com/Papers/IEEE_Software_JulAug_2004_revised.htm" note="Scott Meyers, 'The Most Important Design Guideline?', IEEE Software, July/August 2004. Argues that interface design is where most avoidable defects are prevented or created.">IEEE Software in 2004</LinkNote>: make interfaces easy to use correctly and hard to use incorrectly. I've agreed with it for most of my career without ever doing much about it, because writing the enforcement cost more than the misuse did. An analyzer doesn't read your code as text - it reads a <Define term="syntax-tree">syntax tree</Define>, and every time it wants to know what a name in that tree actually refers to, it has to ask the <Define term="semantic-model">semantic model</Define>. Then each rule needs tests proving it fires on exactly the right span and nowhere else. Several days per handful of rules, against a problem the documentation already covered in plain English.

Agents moved both halves of that sum. They misuse a library faster than any team of people can, so the misuse costs more, and the rules I'd been putting off took two days to build with Claude Code. What the model couldn't supply was the boundary. It wrote the tree-walking quickly, but it couldn't tell me which spans a rule must never touch, so I wrote the assertion that the rule stays quiet on code that only looks like a violation, watched the rule fail it, and narrowed the rule until it passed. A third of the tests that shipped are that kind, and they are what the two days actually went on. Budget an afternoon a rule and expect to spend it there.

I chose every rule myself, because knowing which patterns a library was built to remove, which ones are harmless, and which mistakes are bugs rather than habits comes from watching people use it. None of that is written down anywhere in the source.

## How hard the rule should push

Every rule that runs has a strength, and picking it is the part a markdown file can't do at all. A line in `AGENTS.md` is either read or not read. A rule that runs can inform, warn, or fail the build outright, and each of those does something different to somebody else's afternoon.

Mine ship in three tiers. Rules that catch bugs warn, so they turn up in build output where CI will see them. Rules about idiom only inform, so they surface in an editor and never reach the build. Migration rules ship switched off entirely, because turning every nullable return in a codebase into an `Option` is a project somebody has to schedule. Nothing ships as an error.

A new error is a breaking change, and nobody ships a breaking change in a minor version. But warning is not as safe as it looks either, because plenty of consumers build with <Define term="treat-warnings-as-errors" code>TreatWarningsAsErrors</Define> on, and for them a rule I mark warning fails the build just as hard as an error would - on a version bump they made for some entirely unrelated reason.

Work out how far the rule travels before you pick a tier. Rules ride along with the code that carries them: an analyzer ships inside a <Define term="nuget">NuGet</Define> package, a lint rule ships in a shared config, a CI check applies to every branch at once. Anyone bumping a patch version inherits every rule I have added since their last update. They never opted in, and nothing in a red build tells them that turning it all off is one attribute on a package reference. If a rule of mine fires on code that compiled yesterday, I have broken a build nobody asked me to touch.

So warning is reserved for code that is wrong on its own terms, where I can name the bug rather than just the preference, and everything I merely disagree with informs instead. Some people want ordinary C# with a couple of <Define term="monad">monads</Define> in it and others want every function in the codebase returning one, and I'm not going to referee that. That is the <Define term="diagnostic-severity">severity</Define> line I would want somebody else to hold if I were the one taking the upgrade.

Then make it cheap to get out of a rule in either direction. Half of mine carry a fix the editor applies for you, and silencing any of them takes one severity line and no code change at all. The two mistakes I opened with land on opposite sides of the line, which is why I picked them. The dropped `Result` is a bug I can name without knowing anything about how you write C#, so it warns and it turns up in build output. The guarded unwrap is a preference of mine, so it only informs: it never reaches build output, `TreatWarningsAsErrors` never sees it, and an agent working from a build log never finds out it exists. Anyone who wants that one enforced says so in one <Define term="editorconfig" code>.editorconfig</Define> line:

```ini
dotnet_diagnostic.WM2004.severity = warning
```

Whatever strength a rule ships at, it does the same thing for a developer as it does for a model. A developer sees a squiggle under the mistake before any build runs and without reading a word of documentation, and for half of them the editor offers the fix as well. So write the message inside the rule for a person to read, instead of compressing it into a code and a stub sentence. One of mine explains itself like this:

> A discarded Result throws nothing and reports nothing. Match on it, or propagate it to a caller that will.

That sentence tells a developer why the pattern is wrong, and it gives a model enough to produce the correct fix instead of the nearest one. A rule in `AGENTS.md` reaches exactly one of those two readers, and only when it happens to be read.

## Go down your own list

Open your instruction file and read it line by line, asking of each one whether you could say what is wrong in terms a machine could be pointed at. The lines that can't move stay prose, and they get weighed better once the mechanical rules are out of the context window and no longer competing for the same attention. The ones that can move are worth an afternoon each, and you'll learn something about your own design while you write them - you can't describe a pattern to a compiler without first stating exactly what is wrong with it, and more than once my honest answer was that I had made the wrong thing too easy.

Both mistakes I opened with are now things the compiler finds on its own, every time, without me. The dropped `Result` shows up in the build, the guarded unwrap waits in the editor for anyone who wants it, and each carries a strength I chose on purpose and a sentence that explains itself to whoever meets it next. The paragraph in `AGENTS.md` that they replaced had to be read, understood, and agreed with on every single turn, and now it doesn't have to be read at all.
