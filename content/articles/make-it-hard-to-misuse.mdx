<Define term="waystone-monads">Waystone.Monads</Define> is my port of Rust's `Option` into .NET. An `Option<T>` is either `Some`, holding a value, or `None`, holding nothing, and the type won't let you read the value until you have said what happens when it's missing. <Define term="unwrap-method" code>Unwrap</Define> bypasses that. It returns the value, and throws if there isn't one.

I watched an agent write this against it:

```csharp
if (option.IsSome)
{
    return option.Unwrap();
}

return 0;
```

It compiles, it passes tests, and it returns the right number, so if you saw it in review you would probably approve it. But it's the pattern Waystone.Monads exists to remove. <ArticleLink slug="option-type-in-dotnet">`Option` asks you to say what happens when the value is missing</ArticleLink>, and this code asks whether the value is there and then reads it anyway. <Define term="match-method" code>Match</Define> would do the job, because it takes one branch for `Some` and one for `None` and you can't write it without handling both. What the agent wrote is two statements that have to agree with each other, and nothing keeps them agreeing through the next edit.

The agent kept writing it, and it's a good model. C# developers check before they access, they have done it for twenty years, and the training data is full of it. So the agent wrote what a competent C# developer writes, and nothing in my library told it otherwise.

## Why I stopped adding rules to AGENTS.md

My first thought was to write it down. Add a line to <Define term="agents-md" code>AGENTS.md</Define> — *prefer `Match` over a guarded unwrap* — and move on. That's what everyone does, and it follows from how we've been taught to work with agents, which is that you curate what the model reads and the behaviour follows.

I've <ArticleLink slug="skills-that-teach">spent a long time on instructions that teach rather than dictate</ArticleLink>, and I still think that's the right way to write them. But a written instruction behaves in ways you wouldn't tolerate from anything else you build with. The model reads it, weighs it against everything else in the <Define term="context-window">context window</Define>, and decides — again, on every turn. When it decides against, nothing tells you, so you find out by reading the diff. And each rule you add makes the others weaker, because ten guidelines is ten things the model holds in mind while also solving the problem you actually gave it.

Nobody would ship a type system that worked like that. We put up with it in agent instructions because prose is cheap to write and it feels like doing something.

So put the rule where it runs instead. In .NET that means a <Define term="roslyn-analyzer">Roslyn analyzer</Define>, which the compiler loads and runs over your code on every build, and a <Define term="code-fix-provider">code fix provider</Define>, which offers the correction in your editor. Written that way the rule isn't advice the model weighs any more, and re-checking it costs nothing, because checking is what the compiler is already doing.

My `AGENTS.md` now has one general instruction where it used to have a list, and it says to leave the build clean — so any warning in the output is either a real problem or something I suppressed deliberately. The rules themselves live in the compiler, so nothing has to remember them. I still keep prose in my repositories, but I've stopped adding to it.

## Analyzers stopped being expensive to write

Scott Meyers wrote the rule I keep coming back to in <LinkNote href="https://www.aristeia.com/Papers/IEEE_Software_JulAug_2004_revised.htm" note="Scott Meyers, 'The Most Important Design Guideline?', IEEE Software, July/August 2004. Argues that interface design is where most avoidable defects are prevented or created.">IEEE Software in 2004</LinkNote>: make interfaces easy to use correctly and hard to use incorrectly. He wrote it two decades before anyone was pairing with a language model, and I have agreed with it for most of my career without ever doing much about it. Agents changed that, because they misuse a library faster than any team of people can, and a principle you only meet once a quarter is easy to nod at and forget.

Analyzers ship inside a <Define term="nuget">NuGet</Define> package, so installing a library installs its rules too, with no separate step and nothing to opt into. xunit has shipped `xunit.analyzers` as a dependency for years, and Microsoft's threading library does the same.

I still shipped four major versions without one. An analyzer doesn't read your code as text — it reads a <Define term="syntax-tree">syntax tree</Define>, and every time it wants to know what a name in that tree actually refers to, it has to ask the <Define term="semantic-model">semantic model</Define>. Then each rule needs tests proving its <Define term="diagnostic">diagnostic</Define> lands on exactly the right span and nowhere else. That is several days of work per handful of rules, and I could never justify spending them on something the documentation already said in plain English. So the rules stayed in prose.

I built the whole suite over two days with Claude Code. The 5.5 release carries twenty-seven rules, seven code fix providers covering fourteen of them, and about 4,586 lines of analyzer and test code. Of the 138 test methods that ship with those rules, 45 assert that a rule stays *quiet* on code that looks like a violation and isn't, and those 45 are what the two days actually went on. The model wrote the tree-walking quickly, but it couldn't tell me which spans a rule must never touch, so I wrote the assertion, watched the rule fail it, and narrowed the rule until it passed.

I chose every rule on the list myself, because knowing which patterns the library was built to remove, which ones are harmless, and which mistakes are bugs rather than habits comes from four versions of watching people use it, and none of that is written down anywhere in the source. So I handed over the rules I wanted followed, and the model turned each one into a tree walk, a test suite, and for half of them a fix.

Writing those rules also told me something about my own library that four versions of documentation hadn't. You cannot describe a pattern to a compiler without first stating exactly what is wrong with it, and more than once my honest answer was that the library had made the wrong thing too easy. A <Define term="result-type" code>Result</Define> is either a success value or an error, and it takes an <Define term="implicit-conversion">implicit conversion</Define> from each — but give it the same type on both sides and the two conversions become indistinguishable, so every implicit conversion fails as ambiguous. You can still build and read a `Result<string, string>` the long way round, except that the convenience the type was designed around has gone. Nobody had ever reported it, because nobody had ever had to write the sentence that would have found it.

## Choosing severities

Every rule needs a severity, and picking one is the part of this that a markdown file cannot do at all. A line in `AGENTS.md` is either read or not read. A diagnostic can inform, warn, or fail the build outright, and each of those does something different to somebody else's afternoon.

The rules ship in three tiers. Rules that catch bugs warn, so they turn up in build output where CI will see them. Rules about idiom only inform, so they surface in an editor and never reach the build. Migration rules ship switched off entirely, because turning every nullable return in a codebase into an `Option` is a project somebody has to schedule. Nothing ships as an error.

A new error is a breaking change, and nobody ships a breaking change in a minor version. But warning is not as safe as it looks either, because plenty of consumers build with <Define term="treat-warnings-as-errors" code>TreatWarningsAsErrors</Define> on, and for them a rule I mark warning fails the build just as hard as an error would — on a version bump they made for some entirely unrelated reason.

So I made it cheap to get out of a rule in either direction. Half of them carry a fix the editor applies for you, and silencing any of them takes one severity line and no code change at all. Some people use this library because they want ordinary C# with a couple of <Define term="monad">monads</Define> in it, others want every function in the codebase returning one, and I am not going to referee that. A rule warns when the code is actually wrong, and anything that is merely not how I would have written it informs.

The analyzer ships inside the library's own package, so anyone bumping a patch version inherits every rule I have added since their last update. They never opted in, and nothing in a red build tells them that turning it all off is one attribute on a package reference. If a rule of mine fires on code that compiled yesterday, I have broken a build nobody asked me to touch. So warning is reserved for code that is wrong on its own terms, where I can name the bug rather than just the preference, and everything I merely disagree with informs instead. That is the <Define term="diagnostic-severity">severity</Define> line I would want somebody else to hold if I were the one taking the upgrade.

The guarded unwrap I opened with is an idiom rule, so it only informs. It never reaches build output, `TreatWarningsAsErrors` never sees it, and an agent working from a build log never finds out it exists. Anyone who wants it enforced can say so in one <Define term="editorconfig" code>.editorconfig</Define> line:

```ini
dotnet_diagnostic.WM2004.severity = warning
```

My own repository doesn't set it, because `dotnet format analyzers --severity info` reports the whole tier and applies the fixes in one command, and the rules ship with fix providers precisely so that command works. Anyone who runs it gets the corrections without touching a config file, and anyone who doesn't never hears from those rules at all.

Whatever severity a rule ships at, it does the same thing for a developer as it does for a model. A developer sees a squiggle under the mistake before any build runs and without reading a word of documentation, and for fourteen of the rules the editor offers the fix as well. So I wrote the message inside each rule for a person to read, instead of compressing it into a code and a stub sentence. One of them explains itself like this:

> Checking IsSome and then unwrapping asks the same question twice and relies on the reader to see that the answers agree.

That sentence tells a developer why the pattern is wrong, and it gives a model enough to produce the correct fix instead of the nearest one. A rule in `AGENTS.md` reaches exactly one of those two readers, and only when it happens to be read.

## Which of your instructions could run instead?

An analyzer is what .NET happens to offer, and your language may offer something else. A type that makes the bad state unrepresentable does the same job, and so does a lint rule with an autofix, a schema that rejects a malformed payload, a test that fails on the regression, or a CI check that won't merge. All of them run on their own, cost nothing to run again, fail where you can see it, and say the same thing to a developer and a model. A markdown file does none of that.

So open your own instruction file and go down it line by line, asking which of these could run instead. Plenty of them can't, and that's fine. Mine tells an agent to change only what it must and leave adjacent code alone, and no build step will ever tell an edit I asked for from one I didn't, any more than it can compile taste. Those lines stay prose and get re-weighed every turn, and they get weighed better once the mechanical rules have moved out of the context window and stopped competing with them. The ones that can run are worth an afternoon each, and you'll learn something about your own design while you write them.

The guarded unwrap I opened with has an id now, a severity I chose on purpose, and a sentence that explains itself to whoever meets it next. Anyone who wants it enforced writes one line, once. The paragraph in `AGENTS.md` that it replaced had to be read, understood, and agreed with on every single turn, and now it doesn't have to be read at all.
