An agent wrote this against a library of mine, a .NET port of Rust's <Define term="waystone-monads">`Option` and `Result`</Define>. An `Option<T>` holds a value or holds nothing, and it won't let you read the value until you have said what happens when it's missing. A `Result` is either a success or an error, so a method that can fail says so in its return type instead of throwing.

```csharp
Option<User> user = _users.Find(id);

if (user.IsSome)
{
    var found = user.Unwrap();
    var saveResult = _users.Save(found.Activate());

    saveResult.InspectErr(error => _logger.LogError("Activation failed: {Error}", error));

    return Ok(found.Email);
}

return NotFound();
```

It compiles, it passes tests, and it returns the right thing on the happy path, so if you saw it in review you would probably approve it. There are two mistakes in it and they fail in completely different ways.

The first is the guard. <ArticleLink slug="option-type-in-dotnet">`Option` asks you to say what happens when the value is missing</ArticleLink>. This code asks whether the value is there, then reaches in for it anyway with <Define term="unwrap-method" code>Unwrap</Define>, which throws when there's nothing to return. <Define term="match-method" code>Match</Define> would do the job, because it takes one branch for `Some` and one for `None` and you can't write it without handling both. The guard and the unwrap are two statements that have to agree with each other, and nothing keeps them agreeing through the next edit.

The second one is worse, and you probably read straight past it, because it looks like the error is being handled. <Define term="inspect-err-method" code>InspectErr</Define> runs the logging and then hands the same `Result` straight back, and it's that returned `Result` nobody uses. The save result gets captured, named, and passed to a method, which is what makes the line read as diligence. The failure still goes to a log and no further. The endpoint returns 200 whether the save worked or not. A reviewer scanning for a missing error path finds a logger call and moves on.

The agent kept writing both, and it's a good model. C# developers check before they access, they have done it for twenty years, and the training data is full of it. Logging an error and carrying on is just as well attested. So the agent wrote what a competent C# developer writes, and nothing in my library told it otherwise.

I moved both rules out of prose and into the compiler.

## Why I stopped adding rules to AGENTS.md

My first thought was to write it down:

```markdown
# AGENTS.md

- Prefer `Match` over a guarded `Unwrap`.
- Never leave a `Result` unused.
```

That's what everyone does, and it follows from how we've been taught to work with agents, which is that you curate what the model reads and the behaviour follows. I've <ArticleLink slug="skills-that-teach">spent a long time on instructions that teach rather than dictate</ArticleLink>, and I still think that's the right way to write them.

But writing one well doesn't make it run. The model reads it, weighs it against everything else in the <Define term="context-window">context window</Define>, and decides whether to follow it - again, on every turn. The turns it doesn't, nothing warns you, so you find out by reading the diff. And each rule you add makes the others weaker, because ten guidelines is ten things the model holds in mind while also solving the problem you actually gave it.

Nobody would ship a type system that worked like that. We put up with it in agent instructions because prose is cheap to write and it feels like doing something.

My `AGENTS.md` now has one line where it used to have a list:

```markdown
# AGENTS.md

Leave the build clean.
```

Any warning in the output is either a real problem or something I suppressed deliberately.

## Which of your instructions could run instead

Go down your own file and mark each line with what could enforce it:

```markdown
# AGENTS.md

- Never leave a Result unused.               -> analyzer, lint rule
- Every response body carries a requestId.   -> schema
- Money is never a float.                    -> type
- Don't reintroduce the N+1 in OrderService. -> test
- No merge without a changelog entry.        -> CI check
- Change only what you must.                 -> stays prose
- Match the naming style around you.         -> stays prose
```

The mechanism differs by ecosystem and it barely matters which one you reach for. .NET gave me a <Define term="roslyn-analyzer">Roslyn analyzer</Define>, which the compiler loads and runs over your code on every build, with a <Define term="code-fix-provider">code fix provider</Define> offering the correction in the editor. A lint rule with an autofix does the same job somewhere else, and so does a type that makes the bad state unrepresentable. All of them run on their own, cost nothing to run again, fail where you can see it, and say the same thing to a developer and a model. A markdown file does none of that.

Which line goes where comes down to one question: can you say exactly what is wrong, in terms of something in the code that a machine could be pointed at? *Money is never a float* passes, because a machine can find a `float` holding money. *Match the naming style around you* doesn't, because "the style around you" isn't a thing in the file, it's a judgement about the file.

The lines that fail the question stay prose, and that's fine. Mine tells an agent to change only what it must and leave adjacent code alone. No build step will ever tell an edit I asked for from one I didn't. Those lines also get weighed better once the mechanical rules are out of the context window and no longer competing for the same attention.

Watch for the lines that half-pass, because they're where the work is. *Never leave a `Result` unused* passes cleanly: an unused return value is right there in the syntax. *Prefer `Match` over a guarded `Unwrap`* is closer to the line, because a guard followed by an unwrap is a real pattern a machine can match, but calling it wrong is a preference of mine rather than a bug I can name. Both can run. Only one of them should be loud about it, which is a decision worth its own afternoon.

## Go down your own list

You'll learn something about your own design writing these, because you can't describe a pattern to a compiler without first stating what is wrong with it. More than once my honest answer was that I'd made the wrong thing too easy.

Both mistakes I opened with are now things the compiler finds on its own, every time, without me. The paragraph in `AGENTS.md` that they replaced had to be read, understood, and agreed with on every single turn, and now it doesn't have to be read at all.
