<Define term="tony-hoare">Tony Hoare</Define> invented the null reference in 1965 and later called it his "billion-dollar mistake." Decades on, most codebases still handle a missing value by remembering to check for it, rather than by saying in the type that it might not be there.

In production I kept meeting the same bug: a <Define term="null-reference-exception" code>NullReferenceException</Define> that had gone through code review without anyone catching it, because nothing in the types said the value could be missing. The answer I ended up taking came from Rust, which refuses to have the problem at all.

## Rust has no null

Rust is a systems programming language, the kind you'd reach for instead of C or C++, and it's built around catching whole categories of bug at compile time rather than at runtime. So it has no null. There's no keyword for "nothing here", and if a value can be absent you say so in the type, using a built-in type called `Option`.

An `Option<T>` is one of exactly two things:

- `Some(value)`: the value is here.
- `None`: the value is absent.

That's the whole type, with no secret third state and no "present but actually null." It's a <Define term="sum-type">sum type</Define>, so the shapes a value is allowed to take are written down where the compiler can see them.

You read one back by <Define term="pattern-matching">pattern matching</Define>, writing a branch for each shape:

```rust
match find_user(id) {
    Some(user) => println!("{}", user.name),
    None       => println!("user not found"),
}
```

If you forget the `None` branch the code doesn't compile, and it's a hard error rather than a warning. So you meet absence at the moment you reach for the value, and you can't read `user.name` without first proving there's a user to read it from.

That's the bar I wanted in .NET.

## Why C#'s own answer falls short

C# already has an answer in nullable reference types. Mark a return as `User?` and the compiler warns you when you touch a property without checking it first.

```csharp
public User? FindById(Guid id)
{
    return _context.Users.Find(id);
}
```

A warning is all you get, though, and warnings get suppressed, dismissed, or missed in review. `User?` announces that a value might be null and then asks nothing of the caller, so you can write `user.Name` with no check and the build still succeeds with a squiggle under the line. Rust's version of the same contract fails the build.

## Porting Option to .NET

So I built one. <Define term="waystone-monads" code>Waystone.Monads</Define> is a direct port of Rust's `std::option` to .NET, with the same type and the same two states, and it treats absence as a value you have to handle before you can get past it.

The repository method becomes:

```csharp
public Option<User> FindById(Guid id)
{
    var user = _context.Users.Find(id);
    return user is null ? Option.None<User>() : Option.Some(user);
}
```

`Option.Some(user)` wraps a present value and `Option.None<User>()` stands for its absence, so the return type now says out loud that this lookup might find nothing.

C# has no `match` keyword, so the library gives you a <Define term="match-method" code>Match</Define> method that does the same job:

```csharp
Option<User> result = repository.FindById(id);

return result.Match(
    onSome: user => Results.Ok(user),
    onNone: () => Results.NotFound()
);
```

Both branches are required, because `Match` takes two callbacks and there's no overload that accepts one, so the version that skips the empty case isn't something you can write. Rust gets that guarantee from the compiler's `match` checker and C# gets it from a method signature.

## Composition without the nesting

Handling absence at every step would be exhausting if you had to unwrap and rewrap the value by hand each time, and you don't, because `Option<T>` is a <Define term="monad">monad</Define>. You transform what's inside it with `Map`, you chain further work onto it with `FlatMap`, and you never reach in for the raw value yourself.

<Define term="map" code>Map</Define> transforms the inner value *if it exists*, and leaves `None` untouched:

```csharp
Option<string> email = repository
    .FindById(id)
    .Map(user => user.Email);
```

If the user is absent the result is `None<string>` and the lambda never runs, so there's nothing to null check at the call site.

<Define term="flat-map" code>FlatMap</Define> chains steps that *themselves* return an `Option`, and Rust calls it `and_then`:

```csharp
Option<Order> latestOrder = repository
    .FindById(id)
    .FlatMap(user => orderRepository.FindLatestByUser(user.Id));
```

Each step either produces a value or short-circuits to `None`. Without `FlatMap` you'd get back an `Option<Option<Order>>` and have to unwrap it twice, so it flattens the two into one for you, and the guard clauses that null handling usually piles up never appear.

## When to reach for it

Not everywhere. Nullable reference types are fine for small internal details, where a glance at the surrounding code tells you the value might be missing.

`Option<T>` earns its place at boundaries - repository lookups, external service calls, anywhere absence is a legitimate outcome rather than an edge case. Ask whether the method can honestly return nothing, and when it can, make the return type say so.

You do pay for it. You write `.Match()` where you'd have written an `if`, and it's more to type. But a missing `if` still compiles and a missing `Match` branch doesn't, and I'll take the extra typing for that.
